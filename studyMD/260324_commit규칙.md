## Git Commit 규칙 정리

커밋 메시지는 단순히 기록을 남기는 것이 아니라,  
나중에 변경 이력을 빠르게 이해할 수 있도록 도와주는 중요한 정보다.

좋은 커밋 메시지는 아래 특징을 가진다.

- 어떤 작업을 했는지 한눈에 보인다.
- 커밋 히스토리를 읽기 쉽다.
- 협업할 때 변경 목적을 빠르게 파악할 수 있다.

## 1. 기본 원칙

- 커밋 하나에는 가능한 한 하나의 목적만 담는다.
- 메시지는 짧고 명확하게 작성한다.
- "무엇을 수정했는지"가 바로 드러나게 쓴다.
- 너무 큰 작업은 여러 개의 커밋으로 나누는 것이 좋다.

예:

- 좋은 예: `feat: 로그인 기능 추가`
- 좋은 예: `fix: 회원가입 시 이메일 검증 오류 수정`
- 아쉬운 예: `수정`
- 아쉬운 예: `작업함`

## 2. 추천 형식

가장 많이 사용하는 형식은 아래와 같다.

```text
type: 작업 내용
```

예시:

```text
feat: 게시글 등록 기능 추가
fix: 비밀번호 입력 오류 수정
docs: README 업데이트
```

필요하면 범위를 함께 적어서 더 구체적으로 쓸 수도 있다.

```text
type(scope): 작업 내용
```

예시:

```text
feat(auth): 로그인 기능 추가
fix(user): 프로필 이미지 저장 오류 수정
```

## 3. 자주 사용하는 타입

| 타입 | 의미 | 예시 |
| :--- | :--- | :--- |
| `feat` | 새로운 기능 추가 | `feat: 댓글 작성 기능 추가` |
| `fix` | 버그 수정 | `fix: 로그인 실패 시 예외 처리 수정` |
| `docs` | 문서 수정 | `docs: Git 정리 문서 추가` |
| `style` | 코드 의미 변화 없는 스타일 수정 | `style: 들여쓰기 정리` |
| `refactor` | 기능 변화 없는 코드 구조 개선 | `refactor: 회원 서비스 로직 분리` |
| `test` | 테스트 코드 추가 및 수정 | `test: UserService 단위 테스트 추가` |
| `chore` | 빌드, 설정, 기타 자잘한 작업 | `chore: gradle 설정 정리` |

## 4. 타입별 예시

### `feat`

새로운 기능을 만들었을 때 사용한다.

```text
feat: 회원가입 기능 추가
feat: 게시글 상세 조회 API 추가
```

### `fix`

오류를 수정했을 때 사용한다.

```text
fix: 로그인 시 null 오류 수정
fix: 댓글 삭제 후 목록 갱신되지 않는 문제 해결
```

### `docs`

문서 파일을 추가하거나 수정했을 때 사용한다.

```text
docs: Git commit 규칙 문서 추가
docs: 프로젝트 실행 방법 정리
```

### `style`

코드 동작은 바뀌지 않고 형식만 바뀌었을 때 사용한다.

```text
style: 코드 포맷 정리
style: 불필요한 공백 제거
```

### `refactor`

기능은 같지만 내부 구조를 개선했을 때 사용한다.

```text
refactor: 중복된 회원 검증 로직 분리
refactor: 서비스 계층 메서드 구조 개선
```

### `test`

테스트 코드를 작성하거나 수정했을 때 사용한다.

```text
test: 로그인 서비스 테스트 추가
test: 게시글 조회 테스트 케이스 보완
```

### `chore`

설정 파일이나 빌드 관련 작업처럼 기능과 직접 관련 없는 작업에 사용한다.

```text
chore: application.yml 설정 정리
chore: 의존성 버전 업데이트
```

## 5. 커밋 메시지 작성 팁

- 제목만 봐도 어떤 작업인지 이해되게 작성한다.
- 가능하면 한글 또는 영어 중 하나의 스타일로 일관되게 쓴다.
- 너무 길게 쓰기보다 핵심만 담는다.
- "수정", "변경", "업데이트"만 쓰기보다 무엇을 수정했는지 함께 적는다.

예:

- 아쉬운 예: `fix: 오류 수정`
- 더 좋은 예: `fix: 게시글 저장 시 제목 누락 오류 수정`

## 6. 커밋 단위도 중요하다

좋은 커밋 메시지만큼 중요한 것이 커밋 단위다.

- 기능 추가와 코드 정리를 한 커밋에 같이 넣지 않는다.
- 문서 수정과 기능 수정은 가능하면 나눈다.
- 테스트 추가는 기능 커밋과 함께 넣을지, 별도로 나눌지 일관성 있게 관리한다.

예를 들어 아래처럼 나누면 히스토리를 읽기 쉬워진다.

```text
feat: 회원가입 API 추가
test: 회원가입 API 테스트 추가
docs: 회원가입 요청 예시 문서화
```

## 7. 자주 쓰는 예시 모음

```text
feat: 로그인 기능 추가
fix: 로그인 실패 시 예외 메시지 수정
docs: Git 명령어 문서 업데이트
refactor: 게시글 서비스 로직 분리
test: 게시글 등록 테스트 추가
chore: Gradle 설정 변경
```

## 8. 피하면 좋은 표현

- `최종 수정`
- `진짜 수정`
- `이거 됨`
- `작업`
- `수정`
- `commit`

이런 표현은 나중에 커밋 히스토리를 봤을 때 내용을 파악하기 어렵다.

## 9. 핵심 요약

- 추천 형식은 `type: 작업 내용`이다.
- 커밋 메시지는 짧고 명확하게 작성한다.
- 커밋 하나에는 가능하면 하나의 목적만 담는다.
- `feat`, `fix`, `docs`, `refactor`, `test`, `chore` 정도는 익혀두면 실무와 학습 모두에 도움이 된다.
