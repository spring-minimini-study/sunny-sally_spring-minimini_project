# 오늘 한 것: JWT 개념 이해 + 로그인/회원가입 구현

---
## Spring Security + JWT

### Spring Security
   : “누가 어떤 API에 접근할 수 있는지”를 관리하는 전체 보안 체계
   - 보안 프레임워크
   - 서버 코드 안에서 동작

### JWT
   : 로그인한 사용자인지 증명하는 출입증 데이터
   - 토큰 형식

### JWT 의존성을 추가하지 않아도 회원가입/login/logout 기능 자체는 구현할 수 있다.
#### JWT 방식과 세션 방식 비교
| 구분 | 세션 방식 | JWT 방식 |
|---|---|---|
| 핵심 아이디어 | 서버가 로그인 상태를 기억한다 | 클라이언트가 로그인 증명 토큰을 들고 다닌다 |
| 클라이언트가 저장하는 값 | 세션 ID | JWT 토큰 |
| 서버가 저장하는 값 | 세션 정보 | 기본적으로 저장하지 않음 |
| 대표 저장 위치 | Cookie | LocalStorage, SessionStorage, Cookie 등 |
| 주 사용 환경 | 전통적인 웹 서비스 | REST API, 모바일 앱, SPA |

1. 세션 방식

세션 방식은 사용자가 로그인하면 서버가 로그인 정보를 저장하고, 클라이언트에게는 세션 ID만 전달하는 방식이다.

   1. 사용자가 아이디/비밀번호로 로그인 요청
   2. 서버가 사용자 정보를 확인
   3. 로그인 성공 시 서버가 세션 저장소에 로그인 정보 저장
   4. 서버가 클라이언트에게 세션 ID를 쿠키로 전달
   5. 클라이언트는 이후 요청마다 세션 ID 쿠키를 함께 전송
   6. 서버는 세션 ID를 보고 로그인 사용자인지 확인

   - Stateful(서버가 상태를 가지고 있음)

   - 장점
      - 로그아웃 처리가 쉬움
      - 특정 사용자의 세션을 서버에서 강제로 만료시킬 수 있음
      - 보안 제어가 상대적으로 쉬움
   - 단점
      - 서버 메모리나 저장소를 사용한다.
      - 서버가 여러 대일 경우 세션 공유 필요
      - 트래픽이 많아지면 세션 관리 비용이 증가

2. JWT 방식
: 사용자가 로그인하면 서버가 JWT 토큰을 발급하고, 클라이언트가 이후 요청마다 토큰을 함께 보내는 방식

   1. 사용자가 아이디/비밀번호로 로그인 요청
   2. 서버가 사용자 정보를 확인
   3. 로그인 성공 시 JWT 토큰 발급
   4. 클라이언트가 JWT 토큰 저장
   5. 이후 요청마다 Authorization 헤더에 JWT 토큰 포함
   6. 서버는 토큰의 서명과 만료 시간을 검증
   7. 유효하면 로그인 사용자로 판단

   - Stateless(서버가 상태를 거의 가지지 않음)

   - 장점
      - 서버 확장성이 좋다.
      - 여러 서버가 같은 secret key만 공유하면 토큰 검증이 가능하다.
      - 모바일 어플리케이션 환경에서도 잘 동작한다.
   - 단점
      - 한 번 발급된 토큰을 즉시 무효화하기 어렵다.
      - 토큰이 탈취되면 만료 전까지 악용될 수 있다.
      - Payload는 누구나 볼 수 있으므로 민감한 정보를 넣으면 안 된다.

### 실무에서는 뭘 쓰는가
=> 둘다.
- 세션+쿠키
   -> HttpOnly Secure Cookie
      - HttpOnly: JavaScript를 통해 쿠키에 접근할 수 없게 된다.
      - Secure Cookie:
- JWT
   -> Access Token + Refresh Token
      - Access Token: API 요청에 사용하는, 만료시간 짧은 token
      - Refresh Token: Access Token 재발급에 사용하는, 만료시간 긴 token
   -> 완전 Stateless 아니고 Refresh token은 서버에서 관리


### JWT 구조
   : `Header.Payload.Signature`
   - Header: 토큰의 기본 정보
      ```
      {
      "alg": "HS256",
      "typ": "JWT"
      }
      ```
      => 이 토큰은 JWT이고, HS256 방식으로 서명했다.
   - Payload: 실제로 담고 싶은 사용자 정보를 넣음
      ```
      {
      "userId": 1,
      "email": "test@example.com",
      "role": "USER",
      "iat": 1710000000,
      "exp": 1710001800
      }
      ```
      - 암호화된 것이 아니라 인코딩 된 것.
         - 절대 중요한 정보를 넣으면 안됨
   - Signature: 토큰이 위조되지 않았는지 확인
      - Header + Payload + 서버의 비밀키 = Signature

### Access Token + Refresh Token
   - Access Token만 사용할 때
      - 만료 시간을 길게 하면 탈취 시 악용 가능성
      - 만료 시간을 짧게 하면 자주 다시 로그인해야 함
   - 흐름
      1. 로그인 요청
      2. 서버가 사용자 검증 후 토큰 2개 발급
      3. 클라이언트는 일반 api 요청에는 access token만 보내고 서버는 Access Token을 검증함
      4. Access Token이 만료되면 클라이언트는 Refresh Token을 사용해서 Access Token 재발급 요청
      5. 서버가 Refresh Token 검증 후 새 Access Token 발급
         - Refresh Token Rotation 사용 시 Refresh Token도 함께 새로 발급함
   - 보통 Refresh Token은 서버 저장소에 저장함
      - 이유
         - 로그아웃해도 Refresh Token이 만료 전까지 살아있을 수 있음
         - 강제 로그아웃이 어려움

### Refresh Token Rotation
   - 기본과 다르게 Access Token 재발급 요청이 올 때마다 Refresh Token도 함께 재발급.

### 로그아웃 시
- 세션+쿠키 방식
   - 서버 세션 삭제
   - Session ID 쿠키 무효화
- Access Token만 쓰는 JWT
   - 클라이언트에서 Access Token 삭제(토큰 만료시까지 유효함. 위험!)
- Refresh token 혼용 JWT
   - 로그아웃 시 서버에서 Refresh token 삭제(강제 만료 처리 가능)

### JWT 방식 더 자세히 알기
- Base64로 암호화 함
   - 디버거를 사용해서 쉽게 복호화 가능
- 정보 보호가 아닌, 위조 방지가 목적
