# 오늘 한 것: JWT 개념 이해 + 로그인/회원가입 구현

---

## JWT란 무엇인가

**JSON Web Token** — 서버가 "이 사람은 인증된 사용자다"라는 사실을 JSON으로 만들어서 서명한 뒤 클라이언트에게 넘겨주는 토큰.

핵심은 **서버가 아무것도 기억하지 않는다**는 것이다.  
세션 방식은 서버가 로그인 상태를 DB나 메모리에 저장하지만,  
JWT 방식은 토큰 자체에 모든 정보가 들어 있어서 서버가 받으면 그냥 서명만 확인하면 된다.

---

## 세션 vs JWT 비교

| | 세션 방식 | JWT 방식 |
|--|----------|----------|
| 인증 정보 저장 위치 | 서버 (메모리/DB) | 클라이언트 (토큰) |
| 서버 상태 | 상태 있음 (stateful) | 상태 없음 (stateless) |
| 확인 방법 | 세션 ID로 DB 조회 | 서명 검증만 하면 됨 |
| 서버 여러 대일 때 | 세션 공유 문제 발생 | 토큰만 검증하면 되므로 문제 없음 |
| 토큰 강제 만료 | 서버에서 삭제하면 됨 | 만료 전엔 서버가 막기 어려움 |

이 프로젝트에서 `SecurityConfig`에 `SessionCreationPolicy.STATELESS`를 설정한 이유가 바로 "세션 안 쓴다"는 선언이다.

## JWT 구조

JWT는 `.`으로 구분된 세 덩어리로 생겼다.

```
eyJhbGciOiJIUzI1NiJ9
.eyJzdWIiOiJob25nQGV4YW1wbGUuY29tIiwiaWF0IjoxNzE0MzkwMDAwLCJleHAiOjE3MTQ0NzY0MDB9
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

각 덩어리는 **Base64URL 인코딩**이라 디코딩하면 내용을 볼 수 있다.  
(Base64는 암호화가 아니다. 누구나 열어볼 수 있다.)

### 1. Header

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

어떤 알고리즘으로 서명했는지 적혀 있다. 여기선 HS256.

### 2. Payload (Claims)

```json
{
  "sub": "hong@example.com",
  "iat": 1714390000,
  "exp": 1714476400
}
```

실제로 담긴 데이터. `sub`(subject)에 이메일, `iat`(issued at)에 발급 시각, `exp`(expiration)에 만료 시각.  
`JwtProvider`에서 `.subject(email)`, `.issuedAt(...)`, `.expiration(...)` 으로 넣은 값들이 여기 들어간다.

**중요:** Payload는 암호화가 아니라 인코딩이므로 민감한 정보(비밀번호 등)를 절대 넣으면 안 된다.

### 3. Signature

```
HMAC-SHA256(
  Base64URL(header) + "." + Base64URL(payload),
  시크릿 키
)
```

Header + Payload를 시크릿 키로 해시한 값.  
누군가 Payload의 이메일을 바꿔치기하면 Signature가 맞지 않아서 `isValid()`가 `false`를 반환한다.  
서버만 시크릿 키를 알고 있으므로 외부에서 올바른 Signature를 만들 수 없다.

---

## HS256 알고리즘

**HMAC-SHA256** — 메시지와 시크릿 키를 함께 해싱하는 방식.

```
서명 = SHA256(메시지 + 시크릿 키)
검증 = 받은 토큰을 같은 키로 다시 해싱해서 서명과 비교
```

같은 키를 서명/검증에 모두 쓰므로 **대칭키** 방식이다.  
시크릿 키가 노출되면 누구나 유효한 토큰을 만들 수 있으므로 키 관리가 중요하다.  
(RS256은 개인키로 서명하고 공개키로 검증하는 비대칭 방식 — 지금은 HS256으로 충분하다.)

## JWT 인증 전체 흐름

```
1. 로그인 요청
   클라이언트 → POST /api/v1/auth/login { email, password }

2. 서버에서 토큰 발급
   DB에서 회원 조회 → 비밀번호 검증 → JwtProvider.generate(email)
   → { "data": { "token": "eyJ..." } } 응답

3. 클라이언트가 토큰 저장
   flutter_secure_storage에 보관

4. 이후 모든 요청에 토큰 첨부
   Authorization: Bearer eyJ...

5. 서버에서 토큰 검증 (JwtFilter)
   헤더에서 토큰 추출
   → JwtProvider.isValid() → 서명 확인 + 만료 확인
   → JwtProvider.getEmail() → 이메일 추출
   → SecurityContextHolder에 인증 정보 저장

6. 컨트롤러 실행
   인증된 요청으로 처리됨
```

## BCrypt 비밀번호 암호화

JWT와 함께 오늘 구현한 비밀번호 암호화.

```
평문: "1234"
encode("1234") → "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
encode("1234") → "$2a$10$K8ZuLxJtQ...다른값..."   ← 매번 달라짐 (salt 포함)

matches("1234", "$2a$10$N9qo...") → true
matches("5678", "$2a$10$N9qo...") → false
```

**왜 매번 다른 값이 나오는가?**  
BCrypt는 해시할 때 무작위 salt(소금)를 생성해서 앞에 붙인다.  
`matches()`는 해시 값 앞에 붙어있는 salt를 꺼내서 입력값에 똑같이 적용한 뒤 비교한다.  
그래서 결과값이 달라도 원래 값이 같으면 `true`가 된다.

DB에는 절대 평문 비밀번호를 저장하지 않는다. BCrypt 해시값만 저장한다.

## 오늘 만든 파일 요약

| 파일 | 역할 |
|------|------|
| `JwtProvider.java` | 토큰 생성(`generate`), 이메일 추출(`getEmail`), 유효성 검증(`isValid`) |
| `JwtFilter.java` | 모든 요청에서 토큰을 꺼내 검증하고 SecurityContextHolder에 저장 |
| `SecurityConfig.java` | CSRF 비활성화, STATELESS, 경로별 인증 여부 설정, JwtFilter 등록 |
| `AuthService.java` | 회원가입(BCrypt 암호화 저장), 로그인(비밀번호 검증 + 토큰 발급) |
| `AuthController.java` | `/signup`, `/login` 엔드포인트 |
| DTO 3개 | `SignupRequest`, `LoginRequest`, `LoginResponse` |

## 헷갈렸던 것 / 주의할 것

- `UsernamePasswordAuthenticationToken` 세 번째 인자(authorities)를 빠트리면 `isAuthenticated()`가 `false` → 인증된 요청으로 처리되지 않는다.
- `filterChain.doFilter()`를 반드시 호출해야 요청이 컨트롤러까지 도달한다. 토큰이 없어도 호출한다.
- Payload는 Base64 인코딩이라 누구나 열어볼 수 있다. 비밀번호 같은 민감 정보는 절대 넣지 않는다.
- HS256 시크릿 키는 최소 32바이트. 짧으면 jjwt가 예외를 던진다.
