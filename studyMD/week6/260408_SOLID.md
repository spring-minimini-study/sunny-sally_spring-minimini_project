# SOLID를 실제 `member` 코드로 이해하기

SOLID는 객체지향 설계를 더 좋게 만들기 위한 5가지 원칙이다.

- **S**: 단일 책임 원칙
- **O**: 개방-폐쇄 원칙
- **L**: 리스코프 치환 원칙
- **I**: 인터페이스 분리 원칙
- **D**: 의존 역전 원칙

지금 만든 `MemberController`, `MemberService`, `MemberRepository`, `Member`, `DTO`를 기준으로 이해하면 훨씬 쉽다.

---

## 1. S - 단일 책임 원칙
### Single Responsibility Principle

### 뜻
**하나의 클래스는 하나의 책임만 가져야 한다**는 뜻이다.

즉,
한 클래스가 너무 많은 일을 하면 안 된다.

---

### 현재 코드에서의 예

지금 구조는 대략 이렇다.

- `MemberController` -> 요청 받기
- `MemberService` -> 회원 생성/조회 로직 처리
- `MemberRepository` -> DB 접근
- `MemberCreateRequest`, `MemberResponse` -> 데이터 전달
- `Member` -> 엔티티

이 구조 자체가 이미 단일 책임 원칙을 잘 따르는 방향이다.

---

### 좋은 예

#### Controller
    @RestController
    @RequestMapping("/members")
    public class MemberController {

        private final MemberService memberService;

        public MemberController(MemberService memberService) {
            this.memberService = memberService;
        }

        @PostMapping
        public MemberResponse createMember(@RequestBody MemberCreateRequest request) {
            return memberService.createMember(request);
        }
    }

역할:
- HTTP 요청 받기
- Service 호출
- 응답 반환

---

#### Service
    @Service
    public class MemberService {

        private final MemberRepository memberRepository;

        public MemberService(MemberRepository memberRepository) {
            this.memberRepository = memberRepository;
        }

        public MemberResponse createMember(MemberCreateRequest request) {
            Member member = new Member(
                    request.getName(),
                    request.getEmail(),
                    request.getPassword()
            );

            Member savedMember = memberRepository.save(member);

            return new MemberResponse(
                    savedMember.getId(),
                    savedMember.getName(),
                    savedMember.getEmail()
            );
        }
    }

역할:
- 요청 데이터를 받아서
- 엔티티 만들고
- 저장하고
- 응답 DTO로 변환

즉, 회원 비즈니스 로직만 담당한다.

---

### 나쁜 예

    @Service
    public class MemberService {

        public MemberResponse createMember(MemberCreateRequest request) {
            // 회원 저장
            // 이메일 발송
            // 파일 업로드
            // 로그 파일 기록
            // 문자 발송
            // 포인트 지급
            // 관리자 알림
        }
    }

이건 책임이 너무 많다.

문제점:
- 수정 이유가 많아진다
- 테스트하기 어려워진다
- 코드가 복잡해진다
- 문제 위치를 찾기 힘들어진다

---

### 한 줄 정리
**Controller는 요청 처리만, Service는 비즈니스 로직만, Repository는 DB 접근만 맡는 것**
이것이 단일 책임 원칙이다.

---

## 2. O - 개방-폐쇄 원칙
### Open/Closed Principle

### 뜻
**확장에는 열려 있고, 수정에는 닫혀 있어야 한다**는 뜻이다.

즉,
기존 코드를 자꾸 뜯어고치지 않고 새 기능을 붙일 수 있어야 한다.

---

### 현재 코드에서 생각해볼 수 있는 예

지금은 `MemberService`가 일반 회원 생성만 한다.
그런데 나중에 회원가입 방식이 늘어날 수 있다.

예:
- 일반 회원가입
- 카카오 회원가입
- 구글 회원가입

---

### 나쁜 예

    @Service
    public class MemberService {

        public void signUp(String type, MemberCreateRequest request) {
            if (type.equals("normal")) {
                // 일반 회원가입
            } else if (type.equals("kakao")) {
                // 카카오 회원가입
            } else if (type.equals("google")) {
                // 구글 회원가입
            }
        }
    }

새 방식이 추가될 때마다 기존 코드를 계속 수정해야 한다.

---

### 좋은 예

회원가입 방식을 인터페이스로 분리한다.

    public interface SignUpService {
        MemberResponse signUp(MemberCreateRequest request);
    }

    @Service
    public class NormalSignUpService implements SignUpService {
        @Override
        public MemberResponse signUp(MemberCreateRequest request) {
            // 일반 회원가입
            return null;
        }
    }

    @Service
    public class KakaoSignUpService implements SignUpService {
        @Override
        public MemberResponse signUp(MemberCreateRequest request) {
            // 카카오 회원가입
            return null;
        }
    }

이제 새로운 회원가입 방식이 생겨도
기존 코드를 크게 고치지 않고 새 구현체를 추가하면 된다.

---

### 한 줄 정리
**새 기능을 붙일 때 기존 코드 수정이 최소화되도록 만드는 것**
이것이 개방-폐쇄 원칙이다.

---

## 3. L - 리스코프 치환 원칙
### Liskov Substitution Principle

### 뜻
**부모 타입 자리에 자식 타입을 넣어도 정상적으로 동작해야 한다**는 뜻이다.

즉,
상속이나 인터페이스 구현을 했다면 대체 가능해야 한다.

---

### 예시

    public interface MemberService {
        MemberResponse getMember(Long id);
    }

    @Service
    public class MemberServiceImpl implements MemberService {
        @Override
        public MemberResponse getMember(Long id) {
            return new MemberResponse(id, "kim", "kim@test.com");
        }
    }

컨트롤러가 이렇게 의존한다고 하자.

    private final MemberService memberService;

이때 `memberService` 자리에 `MemberServiceImpl`이 들어가도
문제없이 동작해야 한다.

---

### 나쁜 예

    public interface MemberService {
        MemberResponse getMember(Long id);
    }

    public class BrokenMemberService implements MemberService {
        @Override
        public MemberResponse getMember(Long id) {
            throw new UnsupportedOperationException("조회 불가");
        }
    }

겉으로는 같은 `MemberService` 타입인데,
실제로는 기대한 동작을 하지 않는다.

즉, 대체 가능한 구현체라고 보기 어렵다.

---

### 한 줄 정리
**인터페이스를 구현했거나 상속했다면, 그 타입 자리에 들어가도 기대한 대로 동작해야 한다**
이것이 리스코프 치환 원칙이다.

---

## 4. I - 인터페이스 분리 원칙
### Interface Segregation Principle

### 뜻
**인터페이스는 크고 뭉뚱그리지 말고, 필요한 기능만 작게 나눠야 한다**는 뜻이다.

---

### 나쁜 예

    public interface MemberService {
        MemberResponse createMember(MemberCreateRequest request);
        MemberResponse getMember(Long id);
        void sendEmail();
        void uploadProfileImage();
        void createAdminMember();
        void connectSocialAccount();
    }

이렇게 되면 어떤 구현체는
회원 조회만 필요해도 불필요한 메서드까지 모두 떠안아야 한다.

---

### 좋은 예

기능별로 분리한다.

    public interface MemberCreateService {
        MemberResponse createMember(MemberCreateRequest request);
    }

    public interface MemberQueryService {
        MemberResponse getMember(Long id);
    }

    public interface SocialAccountService {
        void connectSocialAccount(Long memberId);
    }

이렇게 하면 사용하는 쪽이 필요한 기능만 의존하게 된다.

---

### 현재 프로젝트에 대입하면
지금은 `MemberService`가 작아서 괜찮다.
하지만 기능이 계속 많아지면 아래를 한 인터페이스에 다 넣는 건 좋지 않을 수 있다.

- 회원 생성
- 회원 조회
- 회원 수정
- 비밀번호 변경
- 소셜 연동
- 관리자 기능

---

### 한 줄 정리
**한 인터페이스에 너무 많은 기능을 몰지 말고, 필요한 기능만 가지게 나누는 것**
이것이 인터페이스 분리 원칙이다.

---

## 5. D - 의존 역전 원칙
### Dependency Inversion Principle

### 뜻
**구체 클래스보다 추상화에 의존하라**는 뜻이다.

즉,
직접 구현체에 꽂히지 말고 인터페이스 같은 추상적인 것에 의존하라는 말이다.

---

### 나쁜 예

    @Service
    public class MemberService {

        private final MemoryMemberRepository memberRepository = new MemoryMemberRepository();
    }

문제점:
- `MemberService`가 `MemoryMemberRepository`라는 구체 클래스에 직접 묶여 있다
- 나중에 JPA 버전으로 바꾸기 어렵다

---

### 좋은 예

    public interface MemberRepository {
        Member save(Member member);
        Optional<Member> findById(Long id);
    }

    @Repository
    public class JpaMemberRepository implements MemberRepository {
        @Override
        public Member save(Member member) {
            return null;
        }

        @Override
        public Optional<Member> findById(Long id) {
            return Optional.empty();
        }
    }

    @Service
    public class MemberService {

        private final MemberRepository memberRepository;

        public MemberService(MemberRepository memberRepository) {
            this.memberRepository = memberRepository;
        }
    }

이제 `MemberService`는 구체 구현체를 모르고,
`MemberRepository`라는 추상화만 안다.

장점:
- 구현 교체가 쉬워진다
- 테스트가 쉬워진다
- 확장이 쉬워진다

---

### 현재 프로젝트에서 보면
지금 네 코드는 `JpaRepository`를 상속한 인터페이스를 직접 사용하고 있어서
완전히 강의식 DIP 구조는 아니지만,
직접 `new`로 구현체를 고정하는 것보다는 훨씬 유연한 구조다.

---

## 전체를 다시 묶어서 보면

### S - 단일 책임
- `Controller`는 요청 처리
- `Service`는 비즈니스 로직
- `Repository`는 DB 접근

### O - 개방 폐쇄
- 회원가입 방식, 알림 방식, 저장 방식이 늘어나도
- 기존 코드 수정은 최소화하고 구현을 추가한다

### L - 리스코프 치환
- 인터페이스 구현체는 그 인터페이스 자리에 자연스럽게 들어가야 한다

### I - 인터페이스 분리
- 기능이 많아지면 하나의 큰 인터페이스보다 작은 역할별 인터페이스가 좋다

### D - 의존 역전
- 구체 클래스 직접 의존보다 인터페이스 의존이 더 좋다

---

## 현재 코드 기준으로 보면

### 이미 잘 지키고 있는 것
- `Controller`, `Service`, `Repository` 분리
  -> **S**

### 나중에 고민하게 될 것
- 회원가입 방식이 늘어날 때
  -> **O**
- 서비스 인터페이스와 구현체를 분리할 때
  -> **L, D**
- 인터페이스가 너무 커질 때
  -> **I**

---

## 한 줄 요약

SOLID는
**클래스마다 역할을 나누고, 구현을 바꾸기 쉽게 만들고, 필요 없는 의존은 줄이는 설계 원칙**이다.
