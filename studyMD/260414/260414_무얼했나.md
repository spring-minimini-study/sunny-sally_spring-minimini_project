### 1) `JpaRepository<Member, Long>`의 역할과 구조

`MemberRepository`에서
`public interface MemberRepository extends JpaRepository<Member, Long>`
라고 작성한 것은
"`Member` 엔티티를 대상으로 하고, 기본키(PK) 타입이 `Long`인 JPA 저장소 기능을 상속받겠다"는 의미다.

구조를 나눠서 보면:
- `JpaRepository`
  - 스프링 데이터 JPA가 제공하는 인터페이스
  - 기본적인 CRUD와 페이징, 정렬 기능까지 포함하고 있다.
- `<Member, Long>`
  - 제네릭(Generic) 타입 지정
  - `Member`: 어떤 엔티티를 다룰지 지정
  - `Long`: 그 엔티티의 PK 타입이 무엇인지 지정

즉, 이 한 줄만으로도 `MemberRepository`는 아래와 같은 메서드를 바로 사용할 수 있다.
- `save(member)` : 회원 저장
- `findById(id)` : ID로 회원 1건 조회
- `findAll()` : 전체 조회
- `deleteById(id)` : ID로 삭제

상속 구조도 함께 보면 이해가 쉽다.
- `JpaRepository`
- `PagingAndSortingRepository`
- `CrudRepository`
- `Repository`

아래로 갈수록 더 기본 인터페이스이고,
위로 갈수록 더 많은 기능이 추가된다고 보면 된다.

현재 프로젝트 기준으로 보면 `MemberService`에서 실제로
`memberRepository.save(member)`
`memberRepository.findById(memberId)`
를 사용하고 있다.
즉, `MemberRepository` 내부에 직접 구현 코드를 쓰지 않아도
`JpaRepository<Member, Long>`를 상속했기 때문에 기본 DB 접근 기능을 바로 사용할 수 있는 것이다.

또한 아래 메서드도 선언되어 있다.
- `boolean existsByEmail(String email);`

이 메서드는 스프링 데이터 JPA가 메서드 이름 규칙을 해석해서
"email 값이 존재하는지 확인하는 쿼리"를 자동으로 만들어준다.
즉, 기본 기능은 `JpaRepository`가 제공하고,
추가 조건 조회는 메서드 이름으로 확장할 수 있다는 점이 핵심이다.

정리하면,
`JpaRepository<Member, Long>`는
`Member` 엔티티 전용 저장소의 뼈대를 제공하고,
스프링 데이터 JPA가 그 구현체를 런타임에 자동 생성해서
개발자가 반복적인 CRUD 코드를 직접 작성하지 않도록 도와주는 역할을 한다.
